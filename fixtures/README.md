# Fixtures: the reference test set

Each directory is a small repository with known findings, plus `expected.json` (schema: `expectedSchema` in `packages/shared/src/fixtures.ts`).

- `pnpm fixtures` checks that every `expected.json` is valid and consistent with the files, then copies each fixture into a temporary one-commit git repository, runs `qualor scan --dry-run` on it (the TypeScript sources, or the binary named by `QUALOR_BIN`) and compares the report with `compareFixture`.
- Fixtures that cannot pass yet are listed in `tools/fixtures/known-pending.json` with a reason and the mismatch kinds that are tolerated (for example `engine` and `missing-finding` until an analyzer adapter exists). Every other kind (files, metrics, duplication, coverage) must match. They are never skipped.
- Every metric in `expected.json` is computed by hand. Write the working in `notes`.
- Raw analyzer output captured from real tools lives in `packages/shared/test/sarif-samples/` (see Task 14 of the Phase 0 plan).
- Analyzers are real tools. Before the scan the harness adds what a CI workspace would have and a fixture cannot commit: a `node_modules` link to the repo's own devDependencies (for a fixture with `eslint.config.js`) and, from CLI step 10, `target/classes` compiled with `javac` (for a fixture with `pom.xml`).
- A fixture whose expected engine needs a tool that is not installed here (`ENGINE_TOOLS` in `tools/fixtures/run.ts`; for Trivy also its vulnerability database in `/opt/qualor/share/trivy`, which `tools/analyzers/install.sh` installs) is still scanned and checked for everything else, and that engine's findings are reported as "not checked here" (ruling T4). CI installs the pinned toolchain with `tools/analyzers/install.sh` and sets `QUALOR_REQUIRE_ANALYZERS=1`, which turns a missing tool into a failure. To run everything locally without installing the tools, build `tools/analyzers/Dockerfile` (`docker build -t qualor-analyzers tools/analyzers`) and run `pnpm install && QUALOR_REQUIRE_ANALYZERS=1 pnpm fixtures` in a container of it, on a clone of the repository (the host's `node_modules` holds Windows binaries).
- `deps-vulnerable` (plan 2B) holds lockfiles with known vulnerable dependencies. Its findings come from Trivy's vulnerability database, so they are pinned to the snapshot in `tools/analyzers/install.sh`: after `pnpm trivy-db:pin`, run the fixture again (in the Linux image) and add what the newer database knows about these versions, or pick versions whose advisories are old and settled, as these are.
- `csharp-basic` (plan 2D) is a .NET solution. On Linux only (ruling R8; the tools image, CI), the harness runs `qualor dotnet begin`, `dotnet build --no-incremental` and `qualor dotnet end --dry-run` with `XDG_DATA_HOME` in the work directory, so the MSBuild hook never touches the user's profile; elsewhere (Windows, macOS) its `roslyn` findings are "not checked here", because nothing here isolates a real MSBuild build there — not Windows, where the hook would land in the developer's real profile, and not macOS either, since .NET 8 moved MSBuild's user extensions path off `XDG_DATA_HOME` (ruling R6) and `QUALOR_MSBUILD_USER_DIR` only steers the CLI's own write, not the real MSBuild process the harness spawns. `global.json` pins the SDK's 10.0 feature band, and the findings are listed non-exhaustively: after an SDK bump, re-run it in the image and add what the newer analyzers report.
- `sonarqube-import` (plan 3A) also holds `sonarqube/data.json`, the fake SonarQube's data for that repository (invented keys and names, no SonarSource text), and `sonarqube-expected.json`. After the scan the harness plans the import of that data with the real SonarQube client against the fake (`GET` only), matches its statuses to the scan's findings as the import endpoint would, and compares both with `sonarqube-expected.json` (`tools/fixtures/sonarqube-check.ts`). The hashes in `data.json` are SonarQube's line hash (import-sonarqube.md §10.4) of the fixture's lines.
- `python-basic` (plan 8C) covers Ruff with qualor-default (a hardcoded SQL expression, `hashlib.md5`, `subprocess.call(shell=True)`, a mutable default argument, an unused import and a comparison to `None` in `app/store.py`; the test's own `assert` is `S101`, which qualor-default leaves out) and tree-sitter-python's metrics (a match statement, a docstring class). Its findings come from the pinned Ruff (`RUFF_VERSION`): after a Ruff bump, re-run it in the toolbox and review any new or changed findings by hand.
- `html-basic` and `css-basic` (plan 8D) run Qualor's own HTMLHint and stylelint passes (`/opt/qualor/weblint`, `tools/analyzers/install-weblint.sh`): `css-basic` exercises a project `.stylelintrc.json` (stylelint-config-standard, one rule turned off) and `html-basic` Qualor's default rules, plus an Angular-style fragment (`partials/card.html`) that only trips `frame-title-require`. After a bump of the weblint pins, re-run both in the toolbox and review what changed.
- `llm-prompts` (plan 3B) holds `llm/expected.json` and `llm/answers.json`. After the scan the harness builds, from the report and the shared code alone (no server, no model), what the AI assistant would send for each finding (`tools/fixtures/llm-check.ts`): which findings are eligible (the Gitleaks one never is), the server's redaction count on top of the CLI's, the fields sent and the whole explain data object (triage and fix differ only in `task`); that the data sits alone between the prompt's two marker lines, with the forged marker of line 4 escaped and its nonce refused by `buildPrompt`; that no 8-character fragment of the Gitleaks secret reaches any prompt; and how each canned answer is judged (`ok`, a parse failure, or `OUTPUT_REFUSED:<problem>` from `checkFix`). The CLI redacts the snippets only with Gitleaks' findings, so without Gitleaks installed these differences count as Gitleaks' and are "not checked here". After a change of the prompt builder, the bounds or the redaction, print the new expectation with `tsx tools/fixtures/llm-check.ts --print <report.json.gz>` (a `qualor scan --dry-run --output` of a copy of the fixture, in the analyzers image), review it by hand and copy it in; `--print` never writes a file. The fixture's fake key is allowed in the repository's `.gitleaks.toml` by value, path and rule.
- `kotlin-basic` (plan 8E) runs detekt 1.23.8 (`/opt/qualor/lib/detekt`, `tools/analyzers/install.sh`) with the project's own `config/detekt/detekt.yml` (a lower `LongParameterList` threshold and a longer `MagicNumber` allow-list, so a wrong or ignored config shows at once), plus tree-sitter-kotlin's metrics, a duplicated function and a Gradle Kotlin script. Its findings come from the pinned detekt: after a detekt bump, re-run it in the toolbox and review any new or changed findings by hand.
- `swift-basic` (plan 8F) has its own `.swiftlint.yml`, which the CLI reads and filters (config.md §6). Its findings come from the static SwiftLint of `tools/analyzers/install.sh`: after a SwiftLint bump, re-run it in the toolbox, review any new or changed findings by hand, and re-record `cli/test/analyzer-output/swiftlint/basic.sarif` through the `QUALOR_RECORD_SWIFTLINT_SARIF` hook of `cli/src/analyzers/swiftlint-real.test.ts` (its rules trimmed to those the results use).
- `php-basic` (plan 9A) covers tree-sitter-php's metrics (methods with and without a body, a `switch`, a `match`, a template with inline HTML and the alternative `foreach:` syntax) and PHPUnit's Cobertura report (`coverage/cobertura.xml`, a `<source>` directory with file names relative to it). Its findings come from the pinned PHPStan (`PHPSTAN_VERSION`) at Qualor's default level, recorded in `cli/test/analyzer-output/phpstan/basic.json`, and its coverage from PHPUnit 11.5 with pcov: after a bump of either, re-run it in the toolbox, review any new or changed findings by hand and re-record the PHPStan run (both the fixture's findings and the recorded run) or the coverage report. The recorded run is the adapter's own command, in the toolbox: copy `src`, `tests` and `templates` to `/qualor-work/src`, write `PHPSTAN_WRAPPER` to `/qualor-work/qualor-phpstan.php` and `phpstanNeon({ level: 2, input: '/qualor-work/src', deps: null, tmpDir: '/qualor-work/phpstan-tmp' })` to `/qualor-work/phpstan.neon` (both from `cli/src/analyzers/phpstan.ts`), then, in `/qualor-work`, `php -n -d display_errors=stderr -d extension=phar -d extension=tokenizer qualor-phpstan.php /opt/qualor/lib/phpstan/phpstan.phar <out>/basic.json /qualor-work/src analyse --configuration /qualor-work/phpstan.neon --error-format=json --no-progress --no-interaction --memory-limit=2G` (the php options are `PHP_OPTIONS`), and format the result with prettier.
- `ruby-basic` (plan 9B) covers tree-sitter-ruby's metrics (`def`, `def self.`, `case`/`when`, a `rescue` method clause, an `unless` modifier inside a block, a `Gemfile` known by its name, an RSpec file as a test) and RuboCop with qualor-default (seven findings: five Lint cops plus the high Security/MarshalLoad and Security/Eval; the spec's unused block argument is not in qualor-default). Its `.rubocop.yml` is never read (config.md §6): it would turn findings off and on if it were. Its findings come from the pinned RuboCop (`RUBOCOP_VERSION`): after a RuboCop bump, re-run it in the toolbox and review any new or changed findings by hand.
- `go-basic` (plan 9C) is two Go modules (the root and `tools/`), with no dependency outside the standard library, so the Go engines analyse it offline; it covers staticcheck, go vet and gosec, the curated pairs `govet:printf`/`staticcheck:SA5009` and `govet:bools`/`staticcheck:SA4000` on one line each, and a Go coverage profile. Its findings come from the pinned tools of `tools/analyzers/install-go.sh`: after a bump, re-run it in the toolbox, review new or changed findings by hand, and re-record `cli/test/analyzer-output/{staticcheck,govet,gosec}/basic.sarif` through the `QUALOR_RECORD_GO_SARIF` hook of `cli/src/analyzers/golang-real.test.ts`.
